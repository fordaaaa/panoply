# Showcase MCP — design outline

An MCP server that drives a real browser through the web UI an agent just
built, records the run, edits it into a clip you'd actually watch, and pages it
to your phone through [telepager](https://github.com/fordaaaa/telepager).

Nothing here is built. This is a plan to argue with.

**Why this file is in `docs/`.** [CONTRIBUTING.md](../CONTRIBUTING.md) says the
only source files are `commands/*.md` and `mcp/servers.json`; everything else at
the root is generated by `node build.mjs`. A design note is neither, and
`build.mjs` only ever reads `commands/` and rewrites its declared targets — so a
new `docs/` directory is inert to the build and safe to hand-edit. Parts 2 and 3
are about telepager rather than panoply; they live here because they share the
delivery path Part 1 depends on, and splitting them would separate a decision
from its reason.

---

## Part 1 — the showcase server

### What it is

A coding agent finishes a web UI. Today the honest end of that task is "I ran
the build and it compiled." The agent cannot see the thing. Neither can you, if
you're not at the machine.

This server closes that loop. The agent calls it after the build: it opens a
real browser at the URL, walks the feature it just wrote — scroll the landing
page, open the modal, type in the form, submit it, watch the row appear —
records the whole thing, cuts it down to something under a minute with captions
on the key moments, and sends the clip to Telegram. You get a 40-second video on
your phone showing the feature working, and a one-line verdict on whether every
beat did what it claimed.

Two jobs, and they have to stay honest about which is which:

| Job | Output | Who consumes it |
|:--|:--|:--|
| Smoke test | pass/fail per beat, console errors, failed requests | the agent, immediately |
| Showcase | an edited clip, captioned, under ~60s | you, on your phone |

The smoke test is what makes the showcase trustworthy. A pretty video of a
broken page is worse than no video.

**Language: TypeScript on Node.** Playwright's TS API is the reference
implementation; the Python and .NET ports lag, and there is no first-class Rust
binding worth betting on. telepager is Rust, but MCP is a process boundary — the
two never share a build. Use `@modelcontextprotocol/sdk` over stdio.

### Tool surface

Ten tools. Names, purpose, and the shape of the arguments.

**`showcase_start`** — launch a browser, open a context with recording on,
navigate to the URL, return a session id and an accessibility snapshot.

```json
{
  "url":        "http://localhost:5173",
  "viewport":   { "width": 390, "height": 844 },
  "device":     "iPhone 14 Pro",
  "title":      "Invoice filters",
  "storage_state": "/tmp/auth.json",
  "budget_seconds": 45,
  "hard_timeout_seconds": 180
}
```

`device` is a Playwright device descriptor name and overrides `viewport` when
present. Default portrait, not landscape — the clip is going to a phone, and a
1280×720 desktop capture letterboxes into a stripe you can't read. `title`
becomes the title card. `budget_seconds` is the target length of the *edit*;
`hard_timeout_seconds` is the watchdog that kills the run.

**`showcase_snapshot`** — return the accessibility tree with a stable `ref` per
interactive node, the way `@playwright/mcp`'s `browser_snapshot` does. Every
other tool targets nodes by `ref`, not by CSS. This is the single biggest
flakiness win available and it costs one extra tool.

**`showcase_navigate`** — `{ session_id, url, wait_until: "load" | "domcontentloaded" | "networkidle" }`.

**`showcase_scroll`** — `{ session_id, to: {ref} | "top" | "bottom" | {pixels: 800}, duration_ms: 900, caption? }`.
Scrolling is its own tool rather than a generic action because in a showcase it
is *cinematography*, not interaction: it needs a duration and an easing curve so
the camera glides instead of teleporting. `element.scrollIntoView({behavior:
"smooth"})` inside `page.evaluate`, or a rAF tween when the page overrides
scroll behavior.

**`showcase_interact`** — one tool, discriminated on `action`:

```json
{
  "session_id": "s1",
  "action": "click" | "type" | "hover" | "press" | "select" | "check",
  "ref": "e17",
  "label": "the Save button",
  "text": "acme corp",
  "key": "Enter",
  "caption": "Filters apply live"
}
```

Not six tools. Every MCP tool definition is a permanent tax on the agent's
context window — panoply's own README puts `@playwright/mcp` at ~21 tools and
~5k tokens — and click/type/hover/press differ by one field. One tool with a
discriminant is ~600 tokens and the model picks the branch correctly because the
enum is right there. `label` is required and does double duty: it is the human
name in the run report and the fallback caption text.

**`showcase_wait`** — `{ session_id, until: {visible|hidden|text|url|network_idle|animations_settled}, ref?, text?, timeout_ms }`.
Explicit, because the alternative is the agent inserting sleeps, and sleeps are
how you get a video that is 60% waiting.

**`showcase_assert`** — same predicate shapes as `showcase_wait`, plus
`{ description }`. The difference is bookkeeping: an assert is recorded as a
named beat with a pass/fail, appears in the run report, gets a caption, and the
editor holds an extra beat on the frame where it passed. A failing assert does
**not** abort — it records `fail`, screenshots, and continues. You want to see
where it broke.

**`showcase_capture`** — `{ session_id, ref?, full_page?, caption? }`. Returns
the PNG as an MCP image content block so the *agent* can look at it, and marks
the frame as a hold point for the editor. This is the tool that lets the agent
notice its own layout bug.

**`showcase_caption`** — `{ session_id, text, duration_ms, style: "caption" | "callout", ref? }`.
Text with no interaction attached: title cards, "now watch the total update",
an arrow pointing at a `ref`. Separated from the other tools because a good
showcase needs beats where nothing happens but the viewer reads something.

**`showcase_finish`** — `{ session_id, deliver: "telegram" | "path", caption }`.
Stops recording, runs the edit, renders, optionally hands off to telepager.
Returns the run report — per-beat pass/fail, console errors, failed network
requests, duration, output path, delivery status.

**`showcase_abort`** — `{ session_id, reason }`. Kills the browser and renders
whatever exists. A partial clip that ends at beat 6 with "run aborted: timeout"
burned on it is worth more than nothing.

**On granularity.** Two designs were rejected. *One tool per verb* (12–15 tools)
is what `@playwright/mcp` does; it is right for a general driver and wrong here,
because the extra verbs are context tax on a workflow with a fixed shape. *One
`showcase_run(script)` tool* taking a whole JSON storyboard is tempting — one
round trip, no per-step latency — but it destroys the thing that makes this
worth building: the agent seeing a snapshot, noticing the button moved, and
adapting. Batch-and-hope is how you get a video of an agent clicking empty
space. The middle is verb-level tools with `caption` folded into each, so
narration costs no extra round trips.

### The recording pipeline

Three options, and they are not close.

**A. Playwright `recordVideo`.** Set `recordVideo: { dir, size }` on the
context; Playwright writes a WebM/VP8 file per page, finalized only on
`context.close()`. Free, zero dependencies, works everywhere Playwright works.
But: variable frame rate you don't control, no frames available mid-run, no
timestamps you can align beats against, no pause, no cursor drawn. You get an
opaque blob and can only re-encode it blind.

**B. CDP `Page.startScreencast`.** Chrome DevTools Protocol streams
`Page.screencastFrame` events — base64 JPEG plus a `metadata.timestamp` per
frame, acked with `Page.screencastFrameAck`. You own the muxing. Because every
frame carries a wall-clock timestamp, you can align frames to beat boundaries
exactly, freeze on a specific frame, and retime segments independently. Costs:
you assemble it yourself with ffmpeg, and the browser drops frames under load
(the ack protocol is backpressure, so it degrades rather than corrupting).

**C. Xvfb + `ffmpeg -f x11grab` on a headed browser.** The most faithful
rendering there is — real compositor, real scrollbars, real native cursor, real
smooth scrolling. Also Linux-only, needs Xvfb installed, and is useless on the
macOS and Windows laptops this is supposed to run on.

**Recommend B, with A as a `--simple` fallback when CDP isn't available.**

The deciding factor is retiming. A showcase is not a recording, it's an *edit*,
and every editing operation — hold on this frame, run this scroll at 3×, cut
this 4-second network wait to 300ms — needs to know which wall-clock instant
each frame came from. Only B gives that. A can't be edited except by guessing at
timecodes. C wins on fidelity and loses on portability, which is fatal.

Two things B gives up, and how to buy them back:

- **No cursor.** Draw a synthetic one. Inject an overlay layer into the page — a
  `position: fixed` div in a closed shadow root with `pointer-events: none` and
  a huge `z-index` — and animate a cursor sprite to the target's bounding box
  before each click, with a ripple on the click itself. It's captured by the
  screencast natively, so there is no separate compositing pass. Same layer
  renders captions and callout arrows.
- **No smooth native scroll in headless.** Tween it yourself in
  `page.evaluate` with `requestAnimationFrame` and an ease-in-out curve. You
  wanted control over scroll duration anyway.

Title and end cards are the exception: render them as standalone frames and
`concat` them in ffmpeg, since they exist outside any page.

### Getting a watchable clip instead of a 3-minute crawl

The tool enforces the length budget. Not the agent — the agent will always
believe its own demo is interesting.

**The timeline is a list of beats.** Every tool call that carries a `caption` or
an assert opens a beat and records `(t_start, t_end, kind, caption, priority)`.
Everything between beats is connective tissue with no narrative claim on the
viewer's time.

The render pass, in order:

1. **Kill dead air.** Compare consecutive frames; any run of near-identical
   frames longer than 400ms collapses to 200ms. Page loads and network waits
   evaporate here — usually a third of the runtime.
2. **Speed-ramp the connective tissue.** Non-beat segments get
   `setpts=PTS/N`, N starting at 2.5. Scrolls stay near 1× — a sped-up scroll
   reads as a glitch — but navigation and typing take the ramp fine. Typing in
   particular: render the keystrokes at 4× and nobody notices.
3. **Hold the payoff.** Each passing assert and each `showcase_capture` frame
   gets an extra 1.2s freeze, so the viewer's eye lands on the thing that
   proves the feature works.
4. **Burn captions.** ffmpeg `drawtext` with
   `enable='between(t,start,end)'` and a short alpha fade, lower third, plus a
   thin scrim so text survives a light background. Prefer burning over the DOM
   overlay for the final caption pass — you're compositing against the edited
   timeline, not the live page.
5. **Enforce the budget.** Target 45s, hard ceiling 60s. Over budget: raise N
   on non-beat segments to 4, then trim holds to 0.6s, then drop beats by
   ascending priority — asserts last, and never silently. The run report says
   which beats were cut.
6. **Cards.** 1.5s title card with the `title` and the URL, 2s end card with
   the beat tally: `6 beats · 6 passed · 0 console errors`.

Output: MP4, H.264 High, `-pix_fmt yuv420p` (Telegram's players choke on 4:2:2),
`-movflags +faststart` so the moov atom is at the front and
`supports_streaming` actually works, CRF 23, no audio track. Ship
`ffmpeg-static` rather than assuming a system ffmpeg; call it through
`child_process` with an explicit arg array, not a shell string.

At 720×1280, 30fps, CRF 23, 45 seconds of mostly-static UI lands around 2–5MB.
Nowhere near any limit. The limits bite on the failure path, where a 3-minute
unedited fallback capture is the thing that gets sent — see below.

### Delivery

telepager is the right transport and it is the transport the user already has
running. It owns the Telegram connection, it already knows which chat to send
to, and it already refuses to talk to anyone outside `allowed_user_ids`. The
showcase server should not grow its own bot token.

**But telepager cannot send a file today.** `src/telegram.rs` implements exactly
`getMe`, `sendMessage`, `editMessageText`, `sendMessage` with an inline
keyboard, `answerCallbackQuery`, and `getUpdates`. Every one goes through one
private helper:

```rust
let resp = self.http.post(format!("{}/{method}", self.base))
    .json(&body)     // <- JSON only. No file ever goes through here.
    .send().await?;
```

So this is a hard prerequisite, not an integration detail. Concretely, in
telepager:

1. **`Cargo.toml`** — `reqwest` is currently
   `default-features = false, features = ["json", "rustls-tls"]`. Add
   `"multipart"`, and `"stream"` if you want to stream from disk rather than
   read a 40MB file into memory (you do).
2. **`src/telegram.rs`** — add a `call_multipart` sibling to `call_inner` that
   builds a `reqwest::multipart::Form`, and reuses the existing `ApiResponse`
   decode and the `scrub()` token-redaction path. The token is in the URL; a
   multipart error must not be the one place it leaks.
3. **`send_video(chat_id, path, caption, w, h, duration)`** — POST
   `multipart/form-data` to `/sendVideo` with `chat_id`, `caption`,
   `supports_streaming=true`, `width`/`height`/`duration`, and the file as the
   `video` part with a real filename and `video/mp4` content type. Pass the
   dimensions: without them Telegram guesses, and the in-chat preview comes out
   the wrong aspect ratio. Caption cap on media is **1024 characters**, not the
   4096 that `MAX_MESSAGE_LEN` encodes — long text goes in a follow-up
   `sendMessage`.
4. **`send_animation`** for the silent-autoplay path, and `send_document` for
   the give-up path. Same helper.
5. **`src/ipc.rs`** — the `Request` enum gains
   `SendVideo { path: PathBuf, caption: String }`. Daemon and MCP shim are the
   same machine, so a path is a legitimate payload; validate it's a regular
   file, inside a temp dir the server owns, and under the size cap before
   anything is read.
6. **`src/mcp.rs`** — a `send_video` tool alongside `send_message`, so any agent
   can use it, not just this one.

**The 50MB wall.** The Bot API caps bot uploads at 50MB per file (and downloads
at 20MB). The only way past it is running a local Bot API server with `--local`,
which is not something an open-source tool should ask of its users. So the
showcase server degrades, in this order, and says which rung it landed on:

| Size | Action |
|:--|:--|
| ≤ 45MB | `sendVideo` as-is |
| > 45MB | one re-encode at CRF 30, 540px wide, then retry |
| still over | cut to the assert beats only, re-render, retry |
| still over | `sendPhoto` of the best capture + the text run report |

Never fail silently, and never send a file you haven't measured.

**Rejected transports.** Uploading to a host and sending a link: this is the
user's unreleased UI, and the whole point of telepager is that nothing leaves
the machine except through their own bot. Email: another credential to
configure. A link to telepager's local console: not reachable from a phone —
which is exactly Part 2.

### Failure modes to design for now

**Flaky selectors.** Never accept a raw CSS selector across a tool boundary.
Every target is a `ref` from the last snapshot; resolve refs at act time, and on
a miss, re-snapshot once and retry by accessible name before failing the beat.
Playwright's auto-waiting handles the "element exists but isn't clickable yet"
case for free — don't reimplement it with sleeps.

**Animations that never settle.** `networkidle` is a lie on any page with
polling or analytics, and a looping CSS animation means the page is never
"stable". Give `showcase_wait` a `settle_budget_ms` (default 1500) and proceed
anyway when it expires, recording that it did. `animations: "disabled"` on
screenshots freezes them deterministically; do **not** set
`prefers-reduced-motion` globally by default, because on a page whose feature
*is* the animation you would be recording a video of the thing not happening.
It's a fallback, not a setting.

**Auth walls.** Two paths: a `storage_state` JSON file path passed to
`showcase_start` (Playwright's own format, produced once by the human), or an
explicit login beat reading `SHOWCASE_USER` / `SHOWCASE_PASS` from the
environment. Credentials never travel as tool arguments — tool arguments land in
the agent transcript, and the transcript is a file. During any beat where a
`type: "password"` field has focus, blank the video frames.

**Headless vs headed rendering.** Real differences: headless Chromium resolves a
different default font stack (a page relying on a system UI font renders in
something else), overlay scrollbars behave differently, and WebGL/GPU paths
diverge. Use `--headless=new` rather than the legacy mode, bundle a font
fallback check in the preflight, and give `showcase_start` a `headed: true`
escape hatch. On the first run against a project, capture one frame both ways
and diff — if they differ beyond a threshold, say so in the report once rather
than shipping a video that doesn't look like the app.

**A run that hangs forever.** This is the one that actually hurts, because a
hung MCP call blocks the agent and the user gets nothing. Three layers: a
per-tool timeout (default 15s), a session-wide `hard_timeout_seconds` watchdog
owned by the server rather than by any tool call, and a browser process the
watchdog can `SIGKILL`. When the watchdog fires it runs the render on whatever
frames exist and delivers a clip with `run aborted at beat N: timeout` on the
end card. Also: a session whose owning agent disappears has to be reaped —
track the client and close orphaned browsers, or you leak Chromium processes
until the laptop swaps.

**Two videos in flight.** Rendering is CPU-heavy. One render at a time, queued,
and refuse a third session rather than melting the machine the agent is also
compiling on.

### What it deliberately does not do

It is a smoke test and a demo reel. It is not a test suite, and using it as one
will hurt.

- No assertion library, no fixtures, no setup/teardown, no parameterization.
- No cross-browser matrix. Chromium, because CDP screencast is the pipeline.
- No visual regression baselines. There is no golden image, no diff threshold,
  no approval flow.
- No retries and no flake quarantine. It runs once. A failed beat is reported,
  not re-attempted.
- No CI integration and no exit code anyone should gate on. **Do not block a
  merge on this.** It exists to tell a human "here is the thing, working", and
  to catch the class of bug where the page is blank.

If you want the other thing, that's Playwright Test, and it should live in the
repo being tested.

## Part 2 — a Telegram Mini App for telepager

**Status: designed, on hold. Do not start this.** The design is written down so
that the day the hosting question has an answer, nobody has to rediscover it.

### The idea

telepager serves a full console — sessions, live terminal output, the master
chat pane, questions with buttons — from `127.0.0.1` on a random port, gated by
a key in the query string (`src/ipc.rs`, `Endpoint::ui_url`). It's good, and on
a phone it does not exist. Telegram already has the console's audience captive:
a Mini App would put the real UI one tap from the chat, with the terminal pane
and the session list, instead of the text-shaped subset the bot can express.

### Why it's on hold

A Telegram Mini App is an iframe of a URL that Telegram's client fetches. That
URL must be **public HTTPS with a valid certificate**. There is no loopback
exemption, no self-signed allowance, no local mode. That leaves two doors and
both are bad:

**Every user runs their own tunnel.** cloudflared, ngrok, or a Tailscale
funnel. Each is an extra install, an extra account, an extra daemon, and — for
cloudflared and ngrok — a rotating hostname you have to re-register with
BotFather. Worse, it takes a console whose entire security model is "it's on
loopback, plus a key in the URL" and puts it on the public internet. That key
was never designed to be the only thing between a stranger and a UI that spawns
shell processes in your home directory. Doing this responsibly means a real auth
story first, not a tunnel.

**The project runs shared infrastructure.** A relay every user's daemon dials
out to. That is a permanent hosting bill, a TLS and abuse-management job, and —
fatally — a box that terminates TLS in the middle of a channel controlling
agents with filesystem access on other people's machines. An open-source tool
whose selling point is "runs entirely on your machine; no webhook or public URL
needed" cannot ship that as the recommended path.

Neither cost is worth paying for a nicer view of a console that already works.
So it waits.

### The design, for when it doesn't

**Menu button.** BotFather `/setmenubutton`, or programmatically
`setChatMenuButton` with `{"type": "web_app", "text": "Console", "web_app":
{"url": "https://<host>/miniapp"}}`. Per-chat, so it can be set only for chats
in `allowed_user_ids`.

**`initData` validation** — the whole security model, and it must be done
server-side, in Rust, in `telepager`. The client hands the page a raw query
string. The server:

1. Parses it into pairs, removes the `hash` field, and keeps `signature` out of
   the check string too.
2. Sorts remaining pairs by key and joins them as `key=value` with `\n` — the
   *data-check-string*.
3. `secret_key = HMAC_SHA256(key = "WebAppData", msg = bot_token)` — note the
   inversion: the literal string is the key, the token is the message.
4. `expected = HMAC_SHA256(key = secret_key, msg = data_check_string)`, hex.
5. Constant-time compare against the supplied `hash`. Not `==`.
6. Check `auth_date` freshness. Telegram suggests 24h; for a control plane that
   starts processes, use **300 seconds** and re-open on expiry.
7. Parse `user.id` out of the `user` JSON field and check it against
   `config.allowed_user_ids` (`src/config.rs`) — the same gate the bot already
   applies. Reject with 403 and log the id.

telepager has no crypto dependencies today; this adds `hmac` + `sha2` +
`subtle` (or `hmac`'s own `verify_slice`, which is already constant-time). That
is a small, well-audited addition.

Validate once, then mint a short-lived server-side session token and set it as
an `HttpOnly; Secure; SameSite=None` cookie — `SameSite=None` because the page
runs in Telegram's iframe. Re-validating `initData` on every `/api` call is
wasteful and encourages passing it around in query strings. The existing `?k=`
loopback path stays untouched for desktop.

**Adapting the console HTML.** `src/web_page.html` is one self-contained file
today. Changes:

- **Load `https://telegram.org/js/telegram-web-app.js`.** It cannot be inlined
  or vendored — it's the bridge to the native client. This breaks the
  single-file property for the Mini App route only; keep the loopback route
  serving the file as-is.
- **Boot:** `Telegram.WebApp.ready()` then `.expand()`, and
  `.disableVerticalSwipes()` so a scroll in the terminal pane doesn't dismiss
  the sheet.
- **Theme.** The page already drives everything off CSS custom properties
  (`--bg`, `--card`, `--ink`, `--muted`, `--accent`, `--line`). Map
  `WebApp.themeParams` onto them — `bg_color → --bg`, `secondary_bg_color →
  --card`, `text_color → --ink`, `hint_color → --muted`, `link_color`/
  `button_color → --accent` — and re-apply on the `themeChanged` event. That
  replaces the `prefers-color-scheme` block for this route and makes the console
  look native for free.
- **Viewport.** `100vh` is wrong inside the webview; the keyboard resizes it and
  the terminal pane ends up under the input. Drive the layout off
  `WebApp.viewportStableHeight`, updated on `viewportChanged`. The existing
  `--header-h` and spacing scale carry over unchanged.
- **BackButton.** `WebApp.BackButton.show()` when a session tab is open,
  `onClick` to pop back to the session list, `hide()` at the root. Telegram
  users will press it and expect it to work.
- **Live output.** The SSE stream at `/api/events` survives — `EventSource`
  already retries on its own. But the webview is suspended when backgrounded, so
  reconnect on `visibilitychange` and ask for a replay-from-cursor rather than
  assuming the stream was continuous.
- **No mixed content.** The page is on HTTPS; every reference to
  `http://127.0.0.1:<port>` has to become a relative path or it's blocked.

`WebApp.MainButton` for send, and `WebApp.HapticFeedback` on a session state
change, are cheap and make it feel like it belongs.

## Part 3 — further ideas for telepager

Six the user asked for, then four of mine, marked. Each is a paragraph because
each deserves exactly a paragraph until someone decides to build it.

**Voice notes, transcribed.** Walking to the car and saying "kill s3, it's
looping" beats typing it. Telegram delivers a voice note as an OGG/Opus file
reference: `getFile(file_id)` returns a path, then
`https://api.telegram.org/file/bot<token>/<path>` downloads it — capped at
**20MB**, which is ~an hour of Opus, so irrelevant here. Two changes:
`telegram.rs`'s `IncomingMessage` deserializes only `text` today and needs a
`voice: Option<Voice>` field, and something has to transcribe. The honest hard
part is that there is no free, reliable, dependency-light transcriber: shell out
to a `whisper.cpp` binary if one is on PATH, otherwise hand the audio to the
configured master provider if it accepts audio, otherwise say "voice notes need
whisper installed" rather than pretending. Transcribed text then enters the
exact same path as a typed message to the master.

**Terminal screenshots.** Wide TUI output through `sendMessage` is destroyed —
4096-character chunks cut mid-frame and Telegram reflows the lines, so `htop` or
a progress table arrives as confetti. The daemon already owns worker stdout, so
render the last N lines to a PNG and `sendPhoto` it. Rendering options: drive
the existing console page through a headless browser (correct, but a Chromium
dependency in a 3MB Rust binary is absurd), or rasterize directly with
`fontdue`/`ab_glyph` plus `image` and a bundled monospace font, parsing ANSI SGR
into colors. Take the second. Depends on the same multipart work Part 1
requires, which makes it nearly free once that lands.

**`/watch <session>`.** Live-stream a session into one message that keeps
updating, instead of a wall of notifications. `edit_message` already exists and
already swallows "message is not modified" via `is_unmodified`. The constraint
is rate limits: roughly one edit per second per chat, and bursts earn a 429 with
`retry_after`. So coalesce — one edit every 2–3s, only when the tail actually
changed, and honor `retry_after` rather than hammering. Roll to a fresh message
every ~50 edits so the scrollback isn't a single mutating block, and stop on
`/unwatch`, on session exit, or after an idle timeout so a forgotten watch
doesn't burn the chat's rate budget forever.

**Per-session forum topics.** Five concurrent agents in one DM is unreadable.
Telegram forum topics fix it exactly: `createForumTopic` per session, store the
returned `message_thread_id` on the session record, and pass it on every send so
each agent gets its own thread with its own unread badge. The cost is real
setup — the user must create a supergroup, enable topics, add the bot as an
admin with `can_manage_topics`, and telepager's model today assumes a 1:1 DM
(the chat id is derived from `allowed_user_ids`). Worth it for people running
many sessions; make it opt-in config, not the default, and keep the DM path
working untouched.

**Inline approve/deny for shell commands.** Most of this already exists:
`send_with_buttons` renders numbered inline buttons and rides a `question_id` in
`callback_data` (64-byte cap, already handled), and the answer routing works.
The missing half is on the agent side — nothing today intercepts a command
before the master runs it. That needs a chokepoint in the master's execution
path where a proposed command is held pending an answer, with a default-deny
timeout and a persisted allowlist for read-only commands. Without the allowlist
you will tap "approve" forty times in one session and then turn the feature off,
so the allowlist is not a nice-to-have, it's the feature.

**Transcript export.** Sessions already carry an event stream, so rendering one
to Markdown — commands, output, questions, answers, timestamps — is
straightforward. Two exits: `telepager export <session> [--format md|json]` to a
file, and `sendDocument` to Telegram for the phone case, subject to the same
50MB upload cap and needing the same multipart work. Truncate the middle of very
long output rather than the end; the end is where the failure is.

**(my addition) Reply-to-message routing.** `IncomingMessage` already
deserializes `reply_to_message`, so the plumbing is there: replying to a
message that came from session `s3` should address `s3`, rather than the master.
That is a one-field lookup — map outgoing `message_id` to the session that
produced it — and it removes the most common friction in a multi-session chat,
which is saying which agent you meant.

**(my addition) A real bot command menu.** `setMyCommands` populates
Telegram's `/` autocomplete: `/sessions`, `/kill`, `/watch`, `/status`,
`/export`. Discoverability for a bot whose current interface is "know what to
type." Costs one API call at startup and a dispatch table. Pair it with
`t.me/<bot>?start=<payload>` deep links so a message can carry a tappable "open
session s3" rather than an instruction to type something.

**(my addition) Idle and crash watchdog.** The daemon supervises worker
processes, so it knows when one exits nonzero or has produced nothing for ten
minutes — which is when you actually want to be paged, and precisely when
nothing is being sent today because the agent isn't calling any tools. Push
notification on unexpected exit (with the last 20 lines) and on an idle
threshold, both configurable, both off by default. This is the highest
value-per-line item on the list.

**(my addition) Diff review from the phone.** When a worker finishes, send the
`git diff --stat` plus the top few hunks, with approve/request-changes buttons
wired to the same callback machinery as the question flow. It's the one review
action that's genuinely doable on a phone, and it closes the loop the rest of
telepager opens: you started the agent from the couch, you should be able to
accept its work from there too.
